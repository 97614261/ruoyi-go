日期：2026-10-29。分支：portal；基于main/39bc60f。结论：本地工程、独立库、启动结构守卫和基础登录已完成。
这不是CMS、正式两套模板或生产环境验收。

## 已落地

- 专用本地库`ruoyi_go_portal`：20张单租户基线表，加1张`portal_schema_version`。
- 基线来自参考Java仓库`sql/ry_20260417.sql`，完整包含公告已读和代码生成表，不导入ERP数据、
  Quartz表或性能索引脚本；副本和上游许可证保存在`sql/portal/`。基线哈希计算统一LF，避免跨平台换行漂移。
- 新库管理员`admin`使用随机初始密码，明文仅保存于被Git忽略的私有账号文件；基线`ry`账号停用。
- 新库默认任务均停用；门户模式也默认不启动调度器。没有修改原库或ERP的账号、密码、角色或任务。
- 门户使用Redis DB14，安装前核对为空，未清理其他DB；HTTP最终绑定`127.0.0.1:8085`。
- 一份Go二进制提供模板首页、静态资源和已构建后台，服务器不需要Node服务。

## 安装与启动边界

`cmd/portalinit`默认只打印计划，不连接数据库。只有显式`-confirm -admin-config <本地连接配置>`
才允许新建固定名称的本机门户库。已有库、已有门户配置/账号记录或Redis DB14非空就停止，不覆盖。
DDL前先保存本轮私有pending凭据；失败保留现场，不自动删库或重放基线。
成功后生成`configs/portal.local.yml`和`logs/portal-accounts.local.json`，移除本轮pending文件。

启动时仅核对基线版本和结构指纹，不自动迁移、补列或创建表。指纹读取21张表的SHOW CREATE TABLE，
排序后计算摘要；仅剔除随业务新增变化的AUTO_INCREMENT表计数，列/索引/约束等定义仍参与比较。
这是一项启动阶段固定规模元数据检查，不是业务请求中的逐行查询；正常业务分层与N+1约束保持。
未来增加CMS表时，必须在对应显式迁移中升级结构版本/表集合和代码守卫，不能启动时自行接受新结构。
不同MySQL版本恢复后的SHOW CREATE格式可能不同，需要显式迁移复核，不在启动时自动重登记指纹。

## 安装中遇到并修复的问题

第一次安装在基线、管理员和版本表创建后，information_schema读取超时，工具停止且未生成可用私有配置。
只读核实本轮新库21表、空版本记录、无登录/操作及生成业务记录后，用一次性本地续完工具完成初装；
没有重放基线、重建数据库或复用旧ERP库。公共安装器随后补了DDL前pending凭据保存。

服务首次启动的同类元数据扫描也触发15秒deadline。最后改为固定门户表的SHOW CREATE TABLE检查，
更新的仅是本轮门户初装版本指纹，随后实测约70ms并成功启动。失败日志保留为排障记录，
不把失败尝试计作成功验收；公开安装器仍不支持自动续装/重建已有库。

# 拣货与打包使用说明

适用 `erp` 分支，2026-10-26 本地实现。设计见[设计记录](./ERP_PICKING_DESIGN.md)，实际验证与限制见[验收报告](./ERP_PICKING_ACCEPTANCE.md)。这是现有单包裹履约的作业入口，复用原库存事务，无新表、索引或012迁移。

后续已补扫码发货贯穿退货/财务/物流记录的真实接口链路，以及手工与扫码同包裹竞争测试，见[联动补验](./ERP_PICKING_LINK_REVIEW_2026-10-26.md)。两类发货仍是独立权限，不因该验证改变旧手工语义。

原订单/包裹的单笔和批量入口也已补离页保护，见[后续复核](./ERP_FULFILLMENT_LIFECYCLE_REVIEW_2026-10-26.md)：离开阻止尚未发送的确认和后续单据，迟到结果不影响新操作；已经发出的请求仍须回来核对，不代表服务器回滚。

## 1. 开通与员工授权

平台按需给企业开通“ERP工作台 → 拣货与打包”（9600）及按钮9601—9603；企业所有者再给员工角色授权。定义注册不会给已有企业或角色自动加权。

| 权限 | 用途 |
|---|---|
| `erp:picking:list` | 查看当前范围内的包裹列表，默认待发货 |
| `erp:picking:query` | 查看、重新核验并打印一张拣货清单 |
| `erp:picking:check` | 提交当前包裹的完整扫码数量复核 |
| `erp:picking:ship` | 有效复核后，沿原库存事务发货 |

员工还必须同时有该包裹的**店铺范围与仓库范围**。功能权限、企业开通、两类范围互不替代；旧会话也会检查当前授权。平台身份不免除客户业务隔离。

新建“仓库员”角色模板采用上述四项，保留包裹列表/详情/编辑来维护运单，替代原 `erp:package:ship`；已保存角色不自动更新。原手工发货仍由独立的 `erp:package:ship` 授权，不能把手工入口称作已经扫码认证。如果希望仓库员工必须复核后发货，只授予新路径，勿另授予旧手工发货。

## 2. 一单怎样操作

1. 先沿原订单流程审核、分配仓库并预占，得到待发货包裹。
2. 在原包裹页面保存物流及运单，再进入“拣货与打包”，选中包裹；也可从原包裹按钮进入。
3. 核对仓库、商品、规格、单位和应发数量。需要纸单时点击“打印清单”，打印前会重读权限和当前清单。
4. 扫描条码并回车，每次默认记1件；也可手工填写本次数量。页面拒绝错货、多扫；不能少扫后保存。键盘回车只记一次。
5. 全部数量相等后点击“保存复核”，显示“当前版本复核有效”。此时不扣库存。
6. 点击“复核后发货”并确认，服务器重新检查当前权限、范围、版本与复核，才沿原发货事务修改实物、预占、流水和履约状态。

打印时，如果服务器返回的完整清单与原清单一致，会保留尚未提交的扫描数量和输入；条码、版本等信息变化会清空并提示核对，权限拒绝则清空旧详情且不打印。离开页面或重新读取包裹会取消旧打印操作，包括同ID的新读取。相关修复证据见[打印补验](./ERP_PICKING_PRINT_REVIEW_2026-10-26.md)。

一次只操作一个包裹，同SKU多行汇总数量，不混合不同单位；单包裹最多100原行。列表分页上限100。页面清单不包含收件人、电话、地址、运单号或金额；维护运单仍走其独立权限页面。

扫描码来自**当前商品条码**；无条码时使用该包裹的原SKU编码。编码作为字符串精确匹配，保留前导零和大小写。包裹内两个不同SKU使用相同扫描码时，系统阻断复核，需要先修正商品资料。010商品扩展全未安装可用SKU编码退化运行，部分结构损坏必须报错。

支持以键盘输入并发送回车的扫码枪交互，本地验收使用键盘模拟；没有摄像头识别或真实硬件认证。人工输入数量同样可提交，复核只能证明提交数量与系统清单一致，不能证明实物已被拿取。

## 3. 什么会让复核失效

保存复核会推进包裹/订单版本，并在既有不可变事件中记录摘要和指纹；不存完整扫描正文，不制造另一套库存事实。

- 保存物流或其他包裹变更推进版本后，旧复核失效。因此先维护运单再扫描最省事。
- 当前商品条码、规格等扫描清单信息变化，指纹不再一致，必须重新复核。
- 发货前重新检查实时授权、状态、版本及指纹；页面显示有效并不预批准后续提交。

已发货后“本次已扫”显示 `—`，不把清空的页面计数显示成该包裹从未复核。当前清单不是历史条码档案，历史事实仍以事件和库存流水为准。

## 4. 超时、网络断开和重试

如果明确被服务器拒绝，先读取最新清单再处理原因。如果服务器可能已提交但客户端没收到回包，页面冻结**原版本、原请求键和原内容**，使用明确的原请求重试按钮，不自动生成新键重发。

同一员工、同一请求键、同一内容重试返回原结果，不重复复核或扣库；跨员工、改内容重用键会拒绝。重试仍须当前权限和两类范围。页面离开、切换包裹、失活后作废迟到响应，未确认结果不能被旧数据覆盖。

新接口使用HTTP200的业务信封：明确业务拒绝为code400，数据库/提交异常保留code500未知结果。原手工接口不改契约。前端两项写请求跳过通用浏览器防重缓存，幂等由服务端领域请求键负责，避免扫描正文被持久缓存或合法原请求重试在客户端被挡住。

## 5. 接口和维护入口

| 方法与路径 | 请求/结果 |
|---|---|
| GET `/erp/picking/list` | 原包裹过滤/分页，默认 `READY_TO_SHIP` |
| GET `/erp/picking/:packageId` | 当前范围内的最小拣货清单和复核状态 |
| PUT `/erp/picking/:packageId/check` | `version`、`requestKey`、`scans: [{scanCode, quantity}]` |
| PUT `/erp/picking/:packageId/ship` | `version`、`requestKey` |

所有接口要求客户工作区且返回no-store；查询日志不记录该路径的查询正文，通用成功审计不记录扫描正文。领域事件只写最小结果及指纹；接口不能借详情读取客户私有字段。

改动时同步模型、权限定义/契约清单、菜单定义、仓库员模板、前后端和专项测试。新路径不得旁路原发货库存事务，也不能偷偷收紧或改名旧手工权限。

本地验证入口：`scripts/verify-erp.ps1 -Integration -Count 2`。它会在当前配置的专用本地库创建测试资源，不负责升级和备份；按仓库规则检查环境与授权后使用。真实浏览器、实体出纸及实际硬件需另验。本轮没有远程、Linux、容量或生产上线结论。

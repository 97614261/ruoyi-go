## 2. 这一期只做什么

业务链路：**供应商 → 采购单草稿 → 确认采购 → 分批收货并入库 → 收齐完成或关闭余量**。

- 供应商资料、联系人、启停；企业内编码唯一，不做物理删除。
- 一张采购单固定一个供应商、一个到货仓库、一种币种，最多100行，同一SKU只出现一次。
- 草稿可以改明细、价格、币种及备注；供应商/仓库从创建固定；确认时冻结资料快照、数量、币种和价格。
- 每次收货选本次到货数量，点击“确认入库”直接过账；首版不增加收货草稿/审批层。
- 支持部分收货；不得超过采购剩余数量。收齐自动完成，不足部分可明确关闭。
- 可追溯采购单、每批收货、关联IN及库存流水。

不做：询价比价、采购建议算法、自动缺货补货、多个供应商拆单、跨仓收货、采购退货/反收货、在途计入可用库存、批次/序列号、单位换算、运费税费分摊、付款/应付/利润核算、真实渠道API、附件及导入。采购价不是库存成本核算结果，关闭采购也不表示已付款。

现有独立手工IN/PR保持原功能。采购托管IN的撤销/退货暂不提供；确认收货前必须明确提示不可直接撤销。普通盘点仍是库存事实校正，不得伪称采购退货或冲销采购收货。

复合约束必须覆盖：采购单→供应商/仓库，采购行→采购单/SKU，收货→采购单的同一仓库及同企业IN，收货行→同采购单的采购行/收货；不能只给tenant_id或单个ID分别建FK后宣称关系完整。receipt与IN的相同仓库还需在事务内校验。

采购行的 `0 <= received_quantity <= ordered_quantity`、收货正数及状态枚举由服务端强制验证。本地MySQL5.7不能依赖CHECK保证这些不变量；唯一/FK约束与事务测试分别验收。

### 金额和数量

- 数量为整数基础单位，采购行/本次收货行1—十亿，库存仍受现有一万亿总上限约束；0不是本次收货行，未勾选行不提交。
- 单价必填、允许0；数据库 `DECIMAL(20,4)`，金额同精度。金额JSON用规范十进制字符串，不用float64、JS Number或科学计数法。
- 逐行精确计算数量×单价，再求和；每个单价/行额/总额均检查DECIMAL范围。超过4位小数或溢出明确拒绝，不静默截断/四舍五入。
- 服务端计算金额，不信客户端总额；币种为3位字母归一大写，不承诺外部币种/结算规则真实性。没有汇率换算、税务及成本会计。
- 确认时锁定启用的供应商/仓库/SKU，刷新并冻结名称/规格/单位/价格快照；后续主数据改名不能改写历史。单位引用保护覆盖采购草稿，删除SKU由复合FK及业务提示保护。

### 索引预案

唯一键包括企业内供应商编码、采购号/创建键、采购行号/SKU、收货号/关联IN、动作请求键。列表索引优先 `(tenant_id, warehouse_id, status, purchase_id)` 与 `(tenant_id, status, purchase_id)`；供应商筛选另审 `(tenant_id, supplier_id, purchase_id)`；收货/事件按 `(tenant_id, purchase_id, receipt_id/event_id)`，跨采购收货列表按企业/仓库/receipt_id。

这些是待004阶段核对的候选，不能全部无脑落库。按实际SQL/外键需要消重，评估索引宽度，并对带仓库范围、状态和供应商筛选的真实查询EXPLAIN。名称包含搜索不宣称走范围索引；不为所有可筛选字段机械建单列索引。分页固定唯一兜底，每页上限100。

## 5. 采购状态

| 状态 | 允许动作 | 库存变化 |
|---|---|---|
| `DRAFT` 草稿 | 编辑、确认、取消 | 无 |
| `CONFIRMED` 已确认未收货 | 收货、取消、关闭余量 | 收货成功才增加实物 |
| `PARTIAL_RECEIVED` 部分收货 | 继续收货、关闭余量 | 仅本批增加实物 |
| `COMPLETED` 全部收齐 | 只读 | 无新变化 |
| `CLOSED` 关闭余量 | 只读，保留已收事实/关闭原因 | 不回滚已收库存 |
| `CANCELLED` 取消 | 只读，仅从草稿或未收货确认单进入 | 无 |

关闭余量=`ordered_quantity-received_quantity`，只对CLOSED行解释为不再收货；已完成/取消不再关闭。关闭前展示未收数量并要求原因；不把未收改成已收，不提供重新打开。

供应商停用阻止新采购/确认，但允许既有已确认采购按冻结主体继续收货；仓库或SKU停用仍阻止入库。取消/关闭可在主数据停用时执行，但仍需当前功能及仓库范围。创建/编辑/确认不预占、不创建余额、不改变销售可用库存。

## 6. 收货事务、幂等与旧入口

收货只在一个repository事务内完成：校验当前身份/功能/仓库 → 查原请求 → 校验采购版本/状态/行余量 → 新建收货与托管IN → 调用事务内库存过账 → 推进累计已收/状态/版本 → 写不可变事件与脱敏成功审计。任一步失败全部回滚，余额、流水和采购进度不得分次提交。

实现锁序：**当前员工 → 供应商 → 采购单 → 仓库 → 有序SKU → 新收货/IN子行及库存过账**。仓库/SKU必须先于新FK子行插入，避免共享FK锁升级；库存核心重用这些锁，不反向获取供应商/采购锁。旧请求先检查当前范围再回原结果，不需要再锁当前主数据。专项并发竞争已验，不把有限用例当任意负载无死锁的保证。

- 同一采购单的并发收货/关闭/取消以采购单锁串行；不同操作校验持久version。两人提交同一余量只能产生一个合法结果，不能超收。
- 创建有独立不变的创建key/hash；编辑不能改写原指纹。编辑、确认、收货、关闭、取消也各有action/key/hash和最小原结果。
- 指纹包含操作者、目标、动作、输入版本和规范化业务内容；相同键同内容返回原结果，同键异内容拒绝。重放先检查当前身份/功能/仓库范围，再查旧结果；不能用重放绕撤权。
- 已提交后响应丢失，原请求重试返回原收货/IN/版本，不再入库；不要因当前版本已增加而先拒绝合法原请求。原结果不是最新状态，页面需另行刷新。
- 托管IN禁止从旧库存创建重放/编辑/确认/取消等写入口单独操作；普通PR创建/编辑/确认也不得引用它绕开采购规则。先检查当前可读范围，再返回托管提示，避免越权探测。
- 库存凭据和流水可按现有仓库权限看数量，不附带采购价/联系人；跳采购详情仍需采购query。不增加无关店铺授权要求，因为这是企业共享补货，不属于某店铺销售订单。

## 7. 接口与权限预案

供应商、采购单/事件/动作及收货读取/过账/历史接口均已实现。不覆盖现有 `/erp/receipt`（手工入库）及 `erp:receipt:*`。托管保护仅限制旧写入口，既有有范围的库存读取仍可用；实际路径见[采购路由](../internal/router/purchase_routes.go)及[库存路由](../internal/router/erp_routes.go)。

| 接口组 | 路径/动作 | 功能权限 |
|---|---|---|
| 供应商 | GET `/erp/supplier/list`、GET `/:supplierId`、POST基础路径、PUT `/:supplierId` | `erp:supplier:list/query/add/edit` |
| 采购单 | GET `/erp/purchase/list`、GET `/:purchaseId`、POST基础路径、PUT `/:purchaseId` | `erp:purchase:list/query/add/edit` |
| 采购事件 | GET `/erp/purchase/:purchaseId/events`，独立分页，只有脱敏动作信息 | `erp:purchase:query` |
| 采购动作 | PUT `/erp/purchase/:purchaseId/confirm`、`/cancel`、`/close` | `erp:purchase:confirm/cancel/close` |
| 收货作业读取 | GET `/erp/purchase/receivable/list`、GET `/erp/purchase/:purchaseId/receivable` | `erp:purchase:receive`；无价格/联系人DTO |
| 收货过账 | POST `/erp/purchase/:purchaseId/receipts`，含version/requestKey/采购行ID及本次数量 | `erp:purchase:receive` |
| 收货历史 | GET `/erp/purchaseReceipt/list`、GET `/:receiptId` | `erp:purchaseReceipt:list/query`；数量/库存关联，不返回采购价 |

静态路径先于ID路径。新增接口仍先客户工作空间守卫，再校验企业开通∩员工功能∩实时仓库范围；平台身份不能代入。供应商是企业级共享目录，联系人只在query，普通列表不回。采购list不回金额，采购query明确包含价款；receive不隐含query，收货历史不隐含采购详情。采购详情不内嵌无限收货/事件集合，历史分别走分页接口；收货历史可按purchaseId筛选，仍独立检查其权限。

新菜单只登记定义，不为demo/demo-b或已有员工自动开通。不新建供应商资源授权系统；供应商联系人/采购金额均不进入通用正文日志、响应日志或浏览器持久防重缓存，成功审计与业务同事务且只含定位字段。采购失败不回显SQL、联系方式或原始备注；无需引入新依赖。

### 新接口七项预审

1. 列表上限100，详情/一次写入最多100行；不提供无界“全部可选项”，下拉搜索也分页。首版不新增导出。
2. 企业/仓库/状态/供应商/主键及关联唯一索引按上述候选审查；004完成时以实际EXPLAIN留证，不先承诺查询耗时。
3. 批量加载供应商、SKU及行，锁定按有序集合；不沿明细逐项查询主数据。继承现有库存有界写循环，不误称全部SQL已批量化。
4. DB/Redis继承context及已有超时；无外部HTTP、MQ或新异步任务。本地写事务复用READ COMMITTED边界。
5. 权限见表，仓库实时范围约束列表/计数/详情/动作/重放。仅有收货权限可获必要无价格信息，不获采购或供应商完整详情。
6. 使用现有统一response/BizError，普通业务HTTP200中的code保持不变；敏感字段不落通用日志/错误，审计失败整笔回滚。
7. JSON显式camelCase，列表rows/total顶层、详情data；价格/金额字符串，数量整数，状态/企业/累计已收由服务端控制。

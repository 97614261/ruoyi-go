# 新企业从零启用ERP

适用于 `erp` 分支。基础业务已有商品、店铺/配对、采购/退货、仓库/库存、订单/发货/退货、内部应收应付、物流设置与经营概览。
本指南把已有操作串起来，不创建另一套业务数据或审批流。验收证据见[本轮报告](./ERP_ENABLEMENT_ACCEPTANCE.md)，整体边界见[开发蓝图](./ERP_BLUEPRINT.md)。

## 1. 平台准备企业

1. 平台账号进入“租户管理”，开通企业，指定企业编码、所有者和配额。账号密码单独安全交付，不写到公开文档。
2. 核对该企业已开通哪些功能。新企业保持既有开户默认目录初始化规则；本轮没有改成“默认零开通”。已有企业不会因为更新代码而自动获得新菜单。
3. 如需使用启用检查，为已有企业显式开通ERP下的“企业启用”（9500，`erp:setup:list`）。这不是给平台读取客户业务的入口。
4. 所有者使用企业编码登录，在首页进入“企业启用检查”。该页限当前企业所有者，并需要启用检查权限；员工即使拥有同名菜单也不能读取。

平台不代入客户经营数据。企业开通范围、员工功能角色、仓库范围、店铺范围分别约束业务，不能互相替代。

## 2. 按检查页准备

检查页有16个固定项，分“人员与授权”“业务资料”“第一笔业务”三个阶段。点击“去配置 / 查看”进入原有页面，保存后回检查页重新检查。

| 状态 | 含义 |
|---|---|
| 已有记录 | 本企业存在符合条件的记录，仍须核对当前业务和每位员工 |
| 待准备 | 当前未找到符合条件的记录，不等同系统故障，也不是统一强制门槛 |
| 功能未开通 | 缺少对应业务权限；检查页不借此返回业务存在与否 |
| 模块未安装 | 依赖的可选主结构全无；联系部署人员显式安装 |
| 检查失败 | 不展示旧结果，不把DB/超时/部分结构错误伪装成准备完成或未准备 |

先建启用仓库、可用商品SKU、店铺、供应商，按需配对店铺商品，准备内部记账账户。
物流公司/配送方式是可选目录，原手工物流仍可使用。商品可从商品档案管理多SKU，也可沿原SKU入口维护未归组SKU；已经归组的SKU不能从旧入口绕过聚合编辑。

员工与角色也是按需项：个人企业可由所有者直接操作，无需为了把检查页变绿而建立虚假员工。
所有者拥有本企业全部仓库/店铺范围；普通员工默认没有范围，单独分配后才可操作。

## 3. 角色模板怎样用

企业所有者在“角色管理 → 新增”中选择模板，展开核对权限，再点“预填当前模板”。原“确定”按钮才会保存角色，取消不会创建角色。
只预填新角色，不覆盖旧角色、不分配给员工、不配置仓库或店铺、不修改企业开通范围。后续模板更新也不会自动同步已经保存的角色。

| 模板 | 范围 |
|---|---|
| 业务管理员 | 当前已开通ERP业务读写；不含平台、企业开通、员工管理、仓库/店铺范围授权或启用检查 |
| 采购员 | 供应商、含价格采购、收货及原批退货；不含付款记账 |
| 仓库员 | 无价收货、包裹运单维护、拣货/扫码复核后发货、库存读取及调拨；新模板用picking四权限替代package:ship，不含采购价格、订单收件资料或财务 |
| 订单员 | 订单、配对、审核和包裹作业；订单详情可读取收件资料，请按实际岗位授予 |
| 财务员 | 内部应收应付、抵减、核销/冲销及对账；不代表银行转账权限 |

未开通权限会明确列出并排除，只对本企业可授权目录求交集；保存时原角色接口再次校验。
模板应用关闭“父子联动”，按实际ID精确勾选必要节点和父目录，避免勾选父目录后意外选中其他操作。应用前仍请核对明示权限，不把模板名称当作最小授权证明。
模板API需要当前企业所有者及 `system:role:add`，不借启用检查权限授予创建角色能力。

拣货菜单9600—9603仍需企业显式开通；模板更新不会替换已经保存的旧角色。要限制员工必须复核后发货，授予新 `erp:picking:*` 明示四项及必要包裹维护权限，并配置店铺/仓库范围，不另授予旧 `erp:package:ship`。原手工发货独立保留，操作细节见[拣货说明](./ERP_PICKING.md)。

## 4. 完成第一笔业务

1. **采购收货**：准备供应商/仓库/SKU，新增采购草稿，核对单价和币种，确认后分批收货。毛收货、退货和净收货分别保留。
2. **期初库存**：若导入的是已有实物，沿原“采购入库”单据确认形成库存与流水；如已通过真实采购收货入库，不要再录一笔期初库存。当前没有带成本估值的期初账模块。
3. **订单发货**：准备店铺商品与SKU配对，手工录入或模板导入订单，审核分配仓库并预占，先保存手工或目录物流/运单，再在拣货与打包页扫描至应发数量、保存复核、确认发货。另有独立权限的原手工发货；修改运单或商品扫描信息后须重新复核。
4. **内部记账**：按收货批次显式登记应付；已发货且原金额明确的订单显式登记应收，再按币种核销。未知金额不是0；不要为了通过检查创建虚假账单。
5. 回启用检查及经营概览核对；数量、价格、范围和状态仍由各正式业务接口决定，检查页不会锁库存或预批准后续提交。

当前只支持本地手工业务，不含真实渠道授权/同步、自动面单、轨迹、平台结算、退款、库存成本、利润或完整会计。

## 5. 全新本地环境的安装顺序

这不是对已有库执行重建SQL的教程。初始化只允许目标库不存在，并拒绝覆盖配置/登录记录；`sql/multitenant/base.sql`含DROP，不能向现有库直接执行。

1. 准备私有本地配置，独立MySQL/Redis/上传目录；保留原库和现有开发库。不要移除CLI的本地DSN保护。
2. 在目标确认为空的独立环境运行 `tenantinit`，生成独立多租户库、配置和私有登录记录，再运行 `erpinit` 安装001/002及菜单定义；不带 `-grant-demo`。
3. 在同一停写边界备份数据库、公开附件、私有导入附件，在独立恢复库核对结构/行摘要、完整文件清单及登记。报告必须由实际恢复产生，不能复制旧报告或手工勾选checks。
4. 在该次已审查的停写升级窗口内按003→011执行显式CLI，均提供 `-apply -confirm-database ruoyi_go_mt -backup-report <实际报告路径>`，随后不带apply再只读检查。
5. 启动后端，结构校验只能读取；健康检查通过后验证新企业启用和完整业务链，再做包含新业务事实的配套恢复。生产部署须另行设计验证。

CLI顺序：`erpphase1`、`erppurchasing`、`erppurchasereturn`、`erpsalesreturn`、`erpwarehouse`、`erpfinance`、`erpsalesfinance`、`erpcatalog`、`erplogistics`。
现有项目的本地集成入口为 `scripts/verify-erp.ps1 -Integration -Count 2`；它只写专用测试数据，不负责迁移或备份。

本轮在新建且隔离的14306/16380/18082端口实测上述顺序，没有把现有开发库改名或删除后冒充空库。私有演练辅助程序与原生备份保留在本机日志目录，不是仓库公开的一键安装/生产迁移工具。

## 6. 版本交付

先核对本轮源码与既有未提交改动，按[发布清单](./ERP_ENABLEMENT_RELEASE.md)整理。源码、测试、公开SQL和文档可以提交；配置、账号、备份、运行目录、附件、日志和依赖不提交。
本地通过不等于已发布，也不替代目标服务器容量、Linux运行及生产迁移验证。

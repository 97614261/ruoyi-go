# ERP 本地规模与负载测试

这里维护运行方法和测量口径。2026-10-26 的实际结果及未完成/排除项见 [本轮报告](./ERP_CAPACITY_REVIEW_2026-10-26.md)，不能把本页的计划参数当成已测容量。

## 1. 本地只读命令

```powershell
go run ./cmd/erpbench
```

默认仅输出计划，不读配置或凭据、不登录、不发请求。执行必须显式 `-execute`，且通过本地 `ruoyi_go_mt` 与 Redis13 配置校验，目标固定为 `http://127.0.0.1:8081`、GET `/erp/` 路径，不跟随重定向。

```powershell
go run ./cmd/erpbench -execute `
  -token-file logs/erp-load-token.local.json `
  -path '/erp/order/list?pageSize=20' -c 8 -duration 15s -n 10000
```

令牌文件为本地私有 JSON，只有 `token` 字段。使用当轮新建专用测试企业的员工会话，文件留在被 Git 忽略的 `logs/` 中，不粘贴令牌到聊天、命令行、文档或 Git。命令不会建企业、分配权限、修改密码或自动获取验证码；账号和资源须在授权范围内另行准备。

并发上限 256、每档调度最长 2 分钟、最多 250000 个请求、单请求最长 30 秒。默认并发 8、调度 15 秒、上限 10000 请求、单请求超时 10 秒。以时长或请求数先达到者停止继续发送，然后等待已发请求完成；不会为了阶段到时而取消有效请求。

HTTP 200 并不等于成功：响应还必须是业务码 200 的 JSON。超时、HTTP 错误、鉴权/权限/业务失败及正文校验失败均计入结果，不能只报告成功请求的吞吐或延迟。该通用只读命令只校验业务封装，具体行数/范围/二进制内容须由专用场景检查；不能替代权限回归。

```powershell
go test -mod=readonly ./cmd/erpbench ./test/erpload -count=1
go vet -mod=readonly ./cmd/erpbench ./test/erpload
```

这些测试不连接业务库，覆盖默认预览、环境/路径/负载边界、错误计数、请求序号唯一性、在途排空、取消和分位数口径。实际环境不支持 CGO 时，不得把未运行的 `-race` 写成通过。

## 2. 数据与身份

规模测试必须先记录企业水位和旧业务/授权/范围摘要，核对运行二进制及配置。只在本轮新建的专用企业中准备数据，结束撤范围、注销会话、停用保留。不重开已结束的旧测试企业，不动既有企业、原库、远程、账号密码、索引或全局数据库参数。

读取夹具可以批量准备，但必须显著标记、仅限新企业，说明它没有验证用户请求、幂等哈希或完整业务历史。不能把批量插入速度写成服务建单吞吐。普通写入、重放和库存变化应走真实接口/服务事务，分别检查业务结果及最终持久数量。

测试不同企业/仓库/店铺范围时，先证明存在真实可读数据，再检查预期行数、资源 ID 和私有字段。读取固定对象、深分页、COUNT/工作台、经营汇总、导出及写入应分别统计，不能用轻量健康检查或缓存接口的 QPS 代表 ERP 操作。

本轮使用的完整夹具/进程监测/恢复编排在私有验收目录，属于本地测试操作工具，未包装成可对任意库执行的公开造数或生产安装命令。旧 `perfseed`、`scripts/perf.ps1` 面向单租户，不能套用于本分支。

## 3. 并发和统计

测试器采用有界闭环：固定工作协程，一个请求完成后才发下一个，没有用户思考时间。报告并发是同时在途请求上限，不是在线人数、独立登录人数或固定到达率。闭环结果不包含过载后上游请求排队的真实用户等待，不用于承诺互联网流量峰值。

QPS 为全部完成尝试数除以实际持续时间，含在途排空；P50/P95/P99 按全部完成尝试的 nearest-rank 计算，错误不能从延迟样本中抹掉。报告中同时列成功、失败和是否外部取消；预热单列，不能混进正式统计。

每档先校验业务数据，再升并发。出现业务/传输错误、延迟越过预设门槛或资源保护触发时停止升档。主动保护中止的请求要单列，不能当作服务自身故障或无错误的完整阶段；保留中间失败、修正理由及最终结果。

## 4. CPU、内存及依赖

- 同时观测后端、MySQL、Redis、压测端及主机。依赖进程可能服务多个数据库，不能把其全部占用都归到某一接口。
- CPU 用两次累计用户态/内核态时间差或 `process.Percent(0)` 的采样差值。`CPUPercent()` 在当前依赖实现中是自进程创建以来的平均值，不能作为某一阶段的即时 CPU。
- 区分“单核 100%”与“整机 100%”：多核进程前者可以超过 100%；整机百分比需除以逻辑 CPU 数。
- Windows working set/RSS、虚拟/提交内存、Go 活跃堆和数据库缓存并非同一指标。报告样本来源、间隔和缺失项，不能把取不到的进程指标写成 0。
- 健康检查记录数据库连接池、累计等待及 Redis 超时。测试前后看增量，不能把其他轮次留下的累计值当成本阶段错误。
- 观察停止施压后的回落。短时 RSS 不下降并不能证明泄漏；短时间稳定也不能证明长期没有泄漏。

保护条件须在开始前确定，例如主机持续满载、可用内存过低、后端工作集越界或连续健康失败。资源采样和压测都在同一开发电脑时，报告其竞争开销及其他软件影响。

## 5. 解释结果

数据量、筛选条件、权限身份、角色/资源范围、接口权重、预热、并发、时长和硬件应随数字一起保存。深分页随规模变慢、CPU 由 MySQL 消耗较多，只能结合真实 SQL/执行计划解释，不能仅凭经验要求加索引或修改权限语义。

若发现查询没有使用已有唯一索引，应先比较查询计划和结果集，再提出重写；不能绕过索引冻结、改搜索语义或删去当前企业/员工范围。读取 COUNT/深分页问题与建单查重问题应独立评估。

本地 Windows/同机数据库/开发配置的结果，不外推为 2核2G Linux、远程网络、生产服务器、全部 ERP 模块或真实在线用户的容量保证。数据库/附件恢复单独验收，不能用压测通过替代恢复验证。

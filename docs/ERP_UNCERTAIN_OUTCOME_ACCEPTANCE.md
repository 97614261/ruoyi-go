# 操作已提交但成功回包丢失的验收（2026-10-25）

**结论：两轮故障链路、10次成功回包丢失及一次普通链路通过；54张既有业务/授权表摘要一致，最终配套恢复及三组副本业务事实核验通过，本地前后端已恢复运行。**

本轮补[普通业务全链路](./ERP_BUSINESS_FLOW_ACCEPTANCE.md)的一个缺口：已知成功之后再次提交，
不能完整证明“第一次显示网络失败、实际已经提交”的处理正确。因此新增客户端侧故障传输层，
在真实后端返回完整HTTP200且业务code=200之后，丢弃该响应，让这次客户端请求得到明确的模拟网络错误。

## 1. 每次都先证明已经落库

每个故障点执行以下顺序：

1. 用原业务接口发出真实HTTP请求；后端保持正常事务和成功响应。
2. 仅测试客户端隐藏该成功回包，客户端得到网络错误；不在业务代码中加入故障开关。
3. **重试之前**，通过独立查询核对库存、状态或金额已经改变；付款/收款还检查已有一笔记录。
4. 用同一个请求体、原requestKey和原version重试，必须返回`existing=true`的原结果。
5. 后续继续同一批商品的全部链路，核对没有多记账、多扣货或丢掉历史事实。

传输层必须观察到一次完整HTTP200/code200才算命中故障，不把原接口本来失败或未提交算成“成功回包丢失”。
这是客户端测试传输层模拟，边界不扩大为操作系统断网、服务器崩溃或数据库断电。

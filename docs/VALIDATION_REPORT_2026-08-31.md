## 3. Java/Go 契约复核

执行命令：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\contractcheck.ps1 -All -AllowDifferences
```

| 探针 | 一致 | 总数 | 结论 |
|---|---:|---:|---|
| 路由 + 权限标识 | 130 | 130 | 100%，Go 另有专用 `/health` |
| 核心 GET | 36 | 36 | 100% 精确一致 |
| 补充路由场景 | 52 | 57 | 91.23%；其余 5 项为已登记差异 |
| 文件成功/导入 | 4 | 4 | 100% 精确一致 |
| 数据/功能权限 | 18 | 18 | 100% 结果集一致 |
| CRUD | 47 | 60 | 78.33% 精确一致 |
| 非法写入 | 1 | 7 | 行为更严格或错误文案更明确 |
| 校验语义 | 15 | 16 | 双方均拒绝；Java 任务名缺校验入口 |

补充的 57 个场景覆盖了此前未纳入的读取、导出、登录/登出、解锁和写路由。其中破坏性写路由
只执行未登录拒绝场景，证明路由与共同认证边界，不代表已执行其成功副作用。五个不一致场景
归为四类已登记差异：

1. 两个缺失文件下载场景：Go 返回结构化业务错误，Java 返回原始异常文本。
2. 缓存分类：Go 有意隐藏 `login_tokens:`，避免缓存权限暴露完整会话和权限数据。
3. 不存在缓存值：Go 保留完整前缀并返回空串，Java 去掉末尾冒号并返回 `null`。
4. 不存在任务日志详情：Go 返回“不存在”，Java 返回成功和空数据。

本轮还修正了此前未覆盖的三个响应投影：个人资料按 Java 登录会话对象输出，角色已分配/未分配
用户按 Java 的窄列投影输出，用户授权角色页复用 Java 兼容转换。修复后这三类场景精确一致。

其余历史差异不为了数字强行复刻 Java 缺陷：Go 对缺失上传文件给出可读错误、拒绝未知缓存
清理、查询已删除对象返回不存在、保存公告 `remark`，并校验任务名；Java 对应路径会抛内部异常、
静默成功、返回逻辑删除对象、漏写字段或漏校验。完整边界登记在 `DECISIONS.md`。

同一最终前置制品、同一 2C2G 主机、同一数据库/Redis 和同一保存的原始压测器，服务每轮重启并
恢复后执行 c500、20 秒，共三轮：

| 轮次 | QPS | P95 | P99 | 错误 |
|---:|---:|---:|---:|---:|
| 1 | 595.8 | 1451.5ms | 1757.0ms | 0 |
| 2 | 612.1 | 1394.9ms | 1676.2ms | 0 |
| 3 | 639.2 | 1377.8ms | 1419.6ms | 0 |
| 平均 | 615.7 | 1408.1ms | 1617.6ms | 0 |

三轮服务 RSS 峰值 96.0 MiB，服务平均 CPU 约 68.9%（100% 表示占满一个 vCPU），主机总 CPU
平均 98.3%。目标机使用 cgroup v1，根 CPU quota 为 `-1`，`nr_throttled=0`，因此不是容器
CPU quota 节流；压力窗口确实已把 2 个 vCPU 基本占满。

最终源码只比 30 分钟制品多响应层投影和契约探针，不改变压测涉及的六条热路径。部署最终制品
后仍补跑一次 c500/20 秒冒烟：**659.0 QPS、P95 1326.2ms、P99 1478.0ms、0 错误**，处在
前三轮波动区间上沿。

历史约 3000 QPS 仍无法复现；同窗口回放旧制品也只有约 580～641 QPS。当前证据能排除明显
代码回退，但不能证明环境漂移的具体原因，也不能继续把旧数字作为上线承诺。

## 5. 30 分钟混合读写稳定性

场景为 c100 混合读持续 1800 秒，同时每约 10 秒做一轮参数新增、查询、修改和删除，每 5 轮
导出一次用户 XLSX，每 3 轮检查一次健康：

| 指标 | 结果 |
|---|---:|
| 读请求 | 1,303,269 |
| QPS | 724.0 |
| P50 / P95 / P99 / Max | 125.6 / 222.0 / 267.2 / 505.4ms |
| 读错误 | 0 |
| 参数写轮次 / 写错误 | 161 / 0 |
| XLSX 导出 / 导出错误 | 32 / 0 |
| 健康检查 / 健康错误 | 53 / 0 |

服务 RSS 从 67.0 MiB 上升到 76.5 MiB，峰值 77.1 MiB，最后 200 个样本平均 75.9 MiB；本轮
表现为连接池和运行缓存预热后进入窄区间，没有看到持续无界增长，但 30 分钟不能代替数小时的
泄漏观察。服务平均 CPU 69.3%，主机总 CPU 平均 98.5%，说明 c100 已是该 2C2G 的持续饱和
压力而不是舒适余量。

MySQL 池等待 51 次/1092ms；Redis 池等待 3,555,018 次/104,506,268ms（并发累计等待时间），
但超时为 0、结束 pending 为 0。Redis 等待是高并发下的主要排队信号，不能据此把并发上限
继续抬高。生产建议按 **50～80 个同时在途请求** 留余量；100 并发适合作为持续压测档，500
并发只适合短时极限档。这里的“请求并发”不等于在线用户数，后台用户大部分时间不发请求。

## 6. 切换与回滚演练

| 检查 | 结果 |
|---|---|
| Java 服务/进程 | 切换前后均 inactive |
| 清理前会话 | token/index/generation 各 1 |
| 停止旧服务后清理 | 三个前缀均变为 0 |
| 旧 Token | 新版启动后返回 401 |
| 新登录 | token/index/generation 各创建 1 |
| 回滚 | `20260831-final-ea3a17ce` 健康 PASS |
| 恢复 | `20260831-final-e2a6c7da` 健康 PASS |
| 最终状态 | Go active、Java inactive、1 个 Go 进程 |
| 最终会话残余 | 三个前缀均为 0 |
| 验证码 | 数据库 `true`，缓存覆盖不存在 |

清理使用 `SCAN` + 分批 `UNLINK`，没有使用 `KEYS`、`FLUSHDB` 或 `FLUSHALL`，也没有碰验证码、
限流、密码锁定、参数和字典缓存。演练证明当前“停 Java -> 清旧会话 -> 启 Go”的硬切方案和
回滚路径可执行；真实上线仍须先从 Nginx/负载均衡摘流量。

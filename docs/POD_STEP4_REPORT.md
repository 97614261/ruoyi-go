# 第四阶段：执行引擎、可靠任务与测试额度

日期：2026-11-11。本轮实现和验收快照；总体进度见 [POD_DEVELOPMENT_PLAN.md](./POD_DEVELOPMENT_PLAN.md)。设计边界见 [POD_STEP4_DESIGN.md](./POD_STEP4_DESIGN.md)。

## 1. 现在怎么用

1. 打开 `http://127.0.0.1:5177/`，用 `.local/accounts.json` 中的创作账号登录。切换独立 Redis 后，旧浏览器会话需要重新登录；账号密码未变。
2. 创建项目，添加「文本输入」并填写内容，再添加「AI 文本」，将前者的 text 输出连到后者的 text 输入。
3. 点击画布顶部「测试执行」，选择「正常完成」，再点「测试整条流程」。提交前先保存，保存失败/版本冲突时不会创建运行。
4. 在节点和运行面板查看状态及文本结果。结果明确带“测试输出，非 AI 生成”，没有调用外部模型或产生供应商费用。
5. 测试失败时，点击「恢复失败步骤」，同一运行保留成功上游，只恢复已确认失败和被阻断的步骤，最多 5 次。
6. 单节点执行先选中节点；有上游时，从历史选择同项目、同画布版本的运行，复用其中成功的上游输出。缺失输入时拒绝，不自动重跑上游。
7. 顶部「运行」查看跨项目历史；切到「测试额度」查看可用、预占、累计消耗与逐笔流水。

当前执行范围：文本输入、图片输入、测试文本节点。真实生图、图片处理、商品预览和文件导出仍在步骤 5/6 接通。含未实现节点的整条执行明确拒绝，可单独测试可执行节点。

测试场景包含：正常、延迟、首次失败后恢复、持续失败、响应丢失后查询确认。故障场景主要作用于测试文本调用；“延迟”也延迟输入节点，便于检查取消/重启。

## 2. 接口与授权

后端实际路由如下，开发代理加 `/api`。全部要求登录、`pod:studio:access`、本人有效个人空间；管理员不能绕过资源归属。

| 方法/路径 | 请求/结果 |
|---|---|
| `POST /pod/runs` | `projectId/revision/requestId/mode/nodeId/baseRunId/testScenario`，返回 `data` 运行详情 |
| `GET /pod/runs` | `projectId` 可选；`pageNum/pageSize`，返回顶层 `rows/total` |
| `GET /pod/runs/:id` | 固定图快照、节点状态、已确认输出、错误与测试额度 |
| `POST /pod/runs/:id/cancel` | JSON `{}`，停止尚未领取步骤，已领取调用先确认 |
| `POST /pod/runs/:id/retry` | JSON `{"requestId":"新的稳定请求标识"}`，恢复同一运行的失败部分 |
| `GET /pod/credits` | 分页流水 `rows/total`，另有顶层 `account:{available,held,spent}` |

ID、revision、额度均为十进制字符串。列表默认 10、最多 100，运行按 `create_time DESC,run_id DESC`，流水按 `event_id DESC`。
详情最多包含图上限内的节点，不另分页。响应不含存储路径、请求哈希、内部租约、供应商请求键或数据库错误。
业务错误保持 HTTP 200 + code：400 参数，401 未登录，403 空间拒绝，404 不可见记录，409 版本/幂等键/余额/状态冲突，429 等待上限。

创建示例：

```json
{"projectId":"1","revision":"3","requestId":"6b3fe61d-3c69-4318-949c-b57b3bfb4122","mode":"workflow","nodeId":"","baseRunId":"","testScenario":"success"}
```

`mode` 为 `workflow` 或 `node`；单节点需要 nodeId，整条模式不接受 nodeId/baseRunId。requestId 为 16–64 位 ASCII 字母、数字、短横线或下划线。
同空间同 requestId 绑定完整规范化请求；同内容返回原记录，变更内容返回 409。恢复动作有独立请求键唯一约束。
前端超时保留原请求，在同一浏览器会话按账号/空间/项目保存待确认提交，重新打开面板仍用原标识；不会把 Token 放进请求 URL 或该记录。

## 3. 执行、恢复与取消

- 提交事务锁定空间，核对当前项目 revision、图完整性、素材归属、队列上限和余额，再同时写入快照、节点、素材引用、预占流水和 outbox。
- 后续修改/删除项目不改运行图；历史运行继续保护其素材。素材引用数现在是“项目节点引用数 + 历史运行引用数”，不是只统计项目。
- 状态区分 waiting/ready/running/succeeded/failed/blocked/cancelled/awaitingReconciliation；运行另有 queued/cancelRequested。失败阻断后代，独立分支继续。
- Worker 领取时再次检查空间/成员和账号状态；被撤权或停用后，不再启动等待中的调用。已领取调用确认结果后结算，记录仍受空间访问权保护。
- 同一运行恢复失败部分时保留原图和成功输出；新参数或新素材必须保存为新版本并创建新运行。
- 取消不会强停已经提交的供应商调用，也不无条件退款。待确认调用继续保留预占；不能通过“恢复”盲目重提。

节点领取前持久化稳定 submission key、输入和随机 lease token。租约 30 秒，执行中每 10 秒续租，单次调用最多 60 秒。
租约失效后先进入待确认；陈旧进程的心跳与回写被 fencing 条件拒绝。测试执行器支持按稳定键查询；这是本适配器的性质，真实供应商必须另外核对，不能据此宣称任意上游“只执行一次”。

## 4. 队列与并发

Asynq v0.25.1，独立入口 `cmd/worker`。API 与 Worker 可分别启动。Asynq 引入 `golang.org/x/time`，并把既有 cron 从 v3.0.0 提升到兼容的 v3.0.1；继承 Go 单元测试已回归。

MySQL 是事实来源。outbox 保留所有非终态运行，按批最多 50 个扫描，约 5 秒重复检查投递；固定 task ID 每运行最多保留一条相同唤醒任务，避免 Worker 离线时无限堆积重复消息。
入队后丢消息可补投；归档/已完成的残留队列条目在核对状态后移除，下一轮重投。Redis 失败不回滚已经成功的业务提交，也不把任务标成功。
已有 active 队列消息须等待 Asynq 的失联任务恢复，实际恢复延迟还包含其租约、回收周期和重试退避，不承诺崩溃后 5 秒恢复。

默认并发：全局 2、每用户 1、测试供应商 2；未终态运行上限：全局 100、每用户 10，待确认也计入上限。
数据库短事务门闩串行化领取、额度和上限判断；不持锁执行供应商。该方案优先保证本阶段正确性，未做多 Worker 吞吐压测，不能据此宣称高并发性能。

正常停机先停止领取，最多 15 秒排空；已提交工作继续确认。开发 PowerShell 的 stop 会终止核对过身份的进程，属于强制停止，依赖租约恢复；不能把它称为优雅退出。服务信号关闭和进程测试的正常停止路径有独立排空验证。

## 5. 最小测试账本

首次创建运行时发放一次初始测试额度并记录 grant。默认 1000；每个测试文本节点成功消耗 1，输入节点 0。
提交预占本次可能消耗的总量；终态按本次成功节点 settle，剩余 release。恢复失败步骤重新预占剩余部分，不重复结算以前成功的节点。
账户采用 available/held/spent 整数；预占、结算、释放与状态变更在同一数据库事务内，事件键有唯一约束，余额不得为负。
待确认状态保持预占，确认后再结算；取消已成功部分仍收费。这里的“收费”仅指测试单位，无货币价值；未接充值、支付、供应商成本或后台调账。

## 6. SQL、环境与迁移

`004_execution.sql` 新增八张表：`pod_run`、`pod_node_run`、`pod_run_asset_ref`、`pod_outbox`、`pod_credit_account`、`pod_credit_event`、`pod_retry_request`、`pod_execution_gate`。
包含审计字段、空间/历史索引、请求键唯一、大小写敏感节点主键、租约索引和额度事件唯一约束。没有回写已安装的 001–003。
本地已安装 004，服务启动要求 001–004 checksum/实例一致；迁移前 SQL 备份在 `.local/backups/`，尚未做恢复演练。
运行模块用现有生成器输出九个骨架文件供对照（`.local/generated/run/`，忽略提交），适配为私有运行与事务状态机；未开放通用 CRUD 导出、自动管理页或菜单。

真实队列验收发现原本机 Redis 3.0.504 不支持 Asynq 的 Lua 命令。Asynq 至少需要 Redis 4.0，新增启动版本检查。
本轮仅为 POD 下载并启动便携 Windows Redis 5.0.14.1，回环端口 6387、独立密码、DB 15、AOF everysec、128 MiB/noeviction；原 6379 服务及数据未改动。
下载来源为 tporadowski/redis 的 v5.0.14.1 release；压缩包 SHA256：`018ea18a35876383cbb5f4cd0258adfc87747cf9d619bce1cf73a2e36f720ccf`。工具及私密配置都位于忽略提交的 `.local/`。
本地配置切换前副本在 `.local/pod.pre-redis5.yml`，含凭据，不应提交或发到聊天。旧 POD 会话不迁移；SQL 账号未重置。
这只是 Windows 开发验证环境；生产应使用独立维护中的 Redis 与 Linux 验收，不能把该便携版本当作生产推荐。

## 7. 测试证据与剩余验收

主命令：`scripts/pod.ps1 -Action test`；专项 `POD_TEST_CONFIG=...` 后执行 `go test ./test/pod -count=1`。
测试前先停止本项目 Worker；套件检查运行心跳，拒绝在真实 Worker 正消费同库时做可控故障注入，不主动停其他进程。

本轮自动化覆盖：

- 重复/并发提交、内容哈希冲突、重复投递、幂等恢复、唯一结算与整数守恒。
- 成功、延迟、失败阻断、独立分支、仅恢复失败部分；单节点同版本成功上游复用。
- 排队取消、执行中取消、待确认预占、按原键查询，租约过期、陈旧心跳/回写拒绝。
- 全局/用户/供应商并发，等待上限，两个事务竞争仅够一次的余额。
- 跨用户历史/详情/动作拒绝，成员撤权与账号停用，历史素材保护，固定快照与旧 revision 拒绝。
- 103 条同时间夹具验证分页 100 上限、唯一排序、翻页去重及 DTO 不泄漏内部字段。
- 真实 Redis 队列丢任务后补投、独立 Worker 子进程强杀/重启、正常停止排空。
- 前端提交前保存、保存失败不执行、原请求重试与面板重开恢复、单节点参数、额度展示、会话过期及输出转义。

进程崩溃测试在精确新夹具上推进 MySQL 和 Redis 租约时间，并补发重复唤醒，以缩短测试等待；确认重启后使用原 submission key、只结算一次。没有把这个加速测试称为实际默认恢复耗时测试。
测试仅创建新的测试账号/角色关联和工作空间；按精确 ID 清理本轮 SQL、素材文件、会话和独立测试队列。首次 Redis 不兼容和崩溃测试遗留也仅在核对不存在运行记录后清理了对应测试队列，未 FLUSHDB。

## 1. 为什么补这一块

已有商品、店铺配对、订单、采购、库存、基础财务及物流闭环；当前首页仍是技术/使用说明页。
订单已有按当前范围的状态统计，但没有统一的业务概览。先把现有数据集中展示，方便发现待办和进入原业务页面。
本期不新增成本、利润、预测或承运商接入，不制造现有业务无法证明的指标。

代码核对依据：

- web/src/views/index.vue：当前首页为工作空间和使用说明。
- internal/repository/order_workbench.go：订单状态已有GROUP BY统计，可复用其范围口径。
- internal/repository/order.go：订单列表按实时店铺范围过滤，不能把订单概览扩大成全企业统计。
- internal/repository/finance_queries.go：应付/供应商对账，金额为精确字符串；逐单待付与超付分开汇总。
- internal/repository/sales_finance_queries.go：应收/店铺对账及现有范围查询。
- internal/router/finance_routes.go、sales_finance_routes.go：财务列表、明细、对账权限分开。
- web/src/views/erp/components/OrderWorkspace.vue：现有深链接仅读取orderId；不能仅拼status参数就声称点击待办会自动筛选。

## 2. 页面范围

新增一个“经营概览”页面，展示业务卡片与原模块入口，不再为每项统计新建菜单。
平台账号继续显示企业管理入口，不进入客户经营数据；既有首页入口和身份说明保留。
新增菜单只注册定义，不自动给旧企业/员工开通。概览入口权限不隐含任何订单、库存或财务权限。

| 区域 | 第一版显示 | 点击去向 |
|---|---|---|
| 订单待办 | 当前待审核、待发货订单数 | 原订单列表按相同状态/范围筛选 |
| 本地发货 | 上海时间今日、近7日已发货包裹数 | 原发货记录及对应时间筛选 |
| 库存提醒 | 有实物库存的仓库+SKU记录数、存在预占的记录数、按既有预警规则命中的记录数 | 库存/预警列表 |
| 采购待办 | 已确认且仍有未收数量、尚未关闭的采购单数 | 对应采购/收货列表 |
| 采购财务 | 按币种分列已登记账的待付、超付 | 原采购应付/供应商对账 |
| 销售财务 | 按币种分列已登记账的待收、超收 | 原销售应收/店铺对账 |

只显示用户有功能权限的区域，且所有数字仍受服务端实时数据范围约束。
“今日新增商品数”“账户现金余额”“销售利润”等不纳入首版，避免把原始录入、内部账户资料或未知成本误称真实经营收益。

## 3. 必须先固定的统计口径

### 时间和事实

- 待审核、待发货、库存、待收货及未核销金额均为当前状态，不套用“今日创建”条件冒充当前待办。
- 今日发货按包裹shipped_at及Asia/Shanghai的自然日边界；近7日明确为含今天的7个自然日，使用半开时间区间。
- 发货计数单位是包裹，本地SHIPPED不代表平台回传、承运商揽收或妥投。
- 卡片显示各自更新时间。各模块独立读取，不承诺整个页面来自同一个数据库快照；明细跳转后可能因其他人操作而变化。

### 数量和金额

- 不把不同SKU、不同单位的onHand直接相加成“总件数”。概览统计库存记录数；具体数量进入仓库+SKU明细查看。
- 预警沿用现有阈值/可用量规则，未设置阈值不能被当作0阈值计算。
- 采购待收数量依据原订购数与毛收货数及既有关单规则；退货不自动重开采购，也不能用净收货数重新制造待收任务。
- 不把待审核订单的原始金额称为已实现销售收入，未知金额不能按0计入收入。
- 金额按币种分行，用MySQL DECIMAL和项目decimalx处理，JSON保持精确字符串。不同币种不求一个总数。
- 待付/超付、待收/超收先逐单分别计算非负余额，再分别汇总，禁止跨单互相抵消。
- 只统计已经登记的应收/应付及有效核销/冲销事实；未登记原退货不自动当作财务抵减。不新增汇率、成本或真实资金操作。

## 4. 权限和接口方案

采用分区域的只读汇总接口，页面按权限分别请求；不提供一个登录即返全部数据的总接口。
新概览入口权限只负责进入页面，每个接口还必须校验对应的既有业务功能权限。

| 区域 | 额外沿用的既有功能权限 | 数据范围 |
|---|---|---|
| 订单 | erp:order:list | 沿原订单列表店铺范围，不能额外放大或静默套用仓库范围改变其口径 |
| 发货 | erp:shipment:list | 实时店铺与仓库共同约束 |
| 库存基础 | erp:stock:list | 当前仓库范围 |
| 库存预警 | 至少具有可读取对应预警数据的现有权限，实施时按现有路由核对，不由概览权限代替 | 当前仓库范围 |
| 采购 | erp:purchase:list；仅收货员工另评估沿其既有无价作业口径，不由收货权限读取采购价格 | 原采购权限及仓库范围 |
| 采购金额 | erp:payable:list；对账跳转另需erp:financeStatement:list | 现有应付范围 |
| 销售金额 | erp:receivable:list；对账跳转另需erp:shopStatement:list | 现有应收店铺/仓库范围 |

接口拟放在/erp/overview下；实施前登记具体DTO、路由和菜单ID，沿既有handler→service→repository分层。
固定数量卡片返回固定DTO；按币种的行列表使用分页，pageSize上限100，不静默截断。
缺失可选模块显示“未安装”；权限不足、加载失败和合法0分别处理。不能以超时/错误时显示0掩盖故障。

不接收客户端tenantId决定归属。伪造shopId/warehouseId、跨企业ID及旧会话撤权仍由服务端拒绝或过滤。
前端不读取第一页列表后自己求全量总数，不循环翻页拼统计，也不遍历每个仓库/店铺逐个查库。
读取不调用创建应收、调整库存、补历史快照等写入函数。首版不加统计缓存、定时汇总表或新增后台任务。

## 5. 实施前的七项检查

1. 固定卡片不是可无限增长的列表；币种明细分页且上限100。
2. 对现有表做带企业/范围条件的聚合，复用已有索引；先检查EXPLAIN及本地样本耗时，不默认增加索引或改表。
3. 每区域固定数量的聚合查询，不按结果行逐项查库；同区域必要的多次读取使用一致读取。
4. DB调用继承请求context/超时；不引入外部HTTP调用或无界后台协程。
5. 概览入口、业务功能权限、实时资源范围分别校验，平台不代入客户数据。
6. 统一响应与脱敏错误；不返回收件资料、原始备注、账号口令或隐藏资源列表。
7. 显式camelCase DTO，数量不允许溢出，金额保持字符串，错误与缺模块不伪装成业务0。

这是现有业务的只读聚合，暂不需要新业务表或012迁移；实际查询发现必须调整结构时，应另列方案，不在实现途中静默改库。
没有新普通CRUD，不为只读卡片伪造生成器表；需要普通业务CRUD时继续先运行现有生成器。

## 6. 五步执行计划

1. **口径与权限定稿**：为每张卡片确定来源字段、过滤条件、时间、币种、权限和明细跳转，固定验收样例。
2. **只读后端**：实现分区域汇总、分页币种明细、模块缺失处理；核对带范围的EXPLAIN，不更改既有写接口/状态机。
3. **紧凑页面与跳转**：业务卡片加必要待办入口；失活/退出清空数据并作废迟到响应。原页面补明确白名单筛选深链接，不能假设现成支持。
4. **自动化测试**：跨企业、仅部分仓库/店铺、功能与范围撤回、未知金额、两币种、跨日边界、退货/冲销、合法0与失败分离、数字与对应明细一致。
5. **本地验收收口**：使用本轮新建企业，真实员工页面和四尺寸；完整两轮回归、旧业务/授权摘要核对、测试范围撤回/验证码恢复/停用保留，记录实际证据。

延续用户边界：只在本地独立环境，不改旧密码、demo权限、原库或远程，不自动Git提交推送。
五步实现与本地接口/页面验收已经执行；各项结果和配套恢复以本轮验收报告为准，不借用此前物流报告冒充本模块证据。

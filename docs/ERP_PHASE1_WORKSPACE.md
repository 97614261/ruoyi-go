## 2. 新接口与数据边界

| 接口 | 权限与行为 |
|---|---|
| GET /erp/order/workbench | erp:order:list；shopId/sourceOrderNo可选，固定total/pendingReview/readyToShip/shipped/cancelled |
| GET /erp/order/:orderId/readiness?warehouseId=... | erp:order:review；实时店铺与所选仓库，已分配仓库也须有权；专用无收件DTO |

原response的data形状、camelCase和业务错误约定不变，no-store。统计在服务端与订单列表相同的实时店铺范围SQL后GROUP BY status，忽略当前状态页签，其他筛选不忽略；列表与统计独立读取，不承诺同一瞬间快照。固定状态计数不是无界列表；计数失败显示“—”而非0。

统计不是全企业大屏：没有实现全局“未配对订单/缺货订单/失败任务”数量统计。缺货依赖仓库和当时库存，按所选仓库逐单检查；失败导入复用现有任务列表/结果/重试页。不能把入口或未配对变种数偷换成订单数。

检查继承请求context/超时，使用只读RR一致快照，最多100原始行，复用正式审核orderLinesForReview的配对解析与每SKU十亿上限，再批量查询SKU及所选仓库余额，无循环逐行查库或外部调用。复用现有tenant/shop/order/status及仓库SKU索引，不增加DDL；没有做容量压测，不承诺任何数据规模恒定耗时。

响应只含orderId/version/status/warehouseId/checkedAt/ready/issues/stocks；stocks为skuId/skuCode/productName/unit/required/available/shortage。不含收件资料、原始整单、幂等hash或权限凭据；有审核权而没有订单query的人可使用最小库存诊断，但不能因此读取订单详情。平台不代入，撤回范围立即影响下一请求。

没有配对、商品未建档/停用或汇总异常时先显示首个阻断原因，修复后重新检查；解析有效后列出SKU缺口。店铺/仓库/SKU启停、订单状态/版本异常也会阻断。检查不预占、不创建库存凭据/包裹/事件，不锁住库存；**检查通过不保证稍后能审核**，正式提交仍重新在事务内校验版本、权限、配对与库存。

## 3. 批量语义与重试

批量是前端串行调用既有单笔审核/取消/包裹发货接口，不新增批量事务接口，也不是持久后台队列。20条是页面单批上限，不是声称限制所有API调用者的总请求数。

确认前复制ID/版本/参数，每行生成一个requestKey；确认和提交期间busy覆盖所有相关输入/关闭动作。不同记录状态不适用、或预检明确阻断的记录逐行SKIPPED，不偷偷丢掉。未做预检也不绕过正式后端校验。

| 页面结果 | 含义 / 后续 |
|---|---|
| 待执行 / 提交中 | 还没有确认结果 |
| 已确认成功 | 正常成功响应或同原请求已成功；后续不重发 |
| 已跳过 | 状态不适用或已检查阻断，未发送该动作 |
| 未确认 | 没有正常成功响应；包括网络丢响应及服务端明确拒绝，不能保证没提交 |

“用原请求重试未确认项”只重发这些行，保持原version/requestKey/仓库/原因，成功项不再发送。批次参数冻结；需要改版本/仓库/原因，应关闭、刷新核对后重选新批次，不自动吞掉版本冲突。请求键保留在当前弹窗内存，不进sessionStorage，也不承诺刷新/重启后续跑。关闭前应核对未确认项；后端仍用状态机和持久幂等保护记账。

每单独立事务，前一单成功不因后一单失败回滚。页面一直显示结果表和各类数量，不用总“成功”提示抹掉部分失败。缺运单先维护物流再发货；本地出库不是平台回传或承运商揽收。

## 4. 详情与交互保护

orderId/packageId/shopId深链接只接受可精确表示的正整数，不将任意query拼SQL。订单/包裹的list/query各自校验，来自另一个业务页面不构成授权；包裹与链接预期orderId不一致时不打开详情。

关闭、链接变化或卸载使旧详情响应失效并清掉收件/物流草稿，换仓库使旧检查失效。列表查询仍有序号保护，旧页不覆盖新页；刷新页清当前选择，不跨页悄悄组成大批次。订单详情展示审核快照，不查询当前配对回填历史；包裹详情仍不返回订单收件资料。

导入结果订单链接仅有order:list和order:query时可点；没有权限只显示ID，不因此授予新权限。页面按钮不是服务端守卫。
